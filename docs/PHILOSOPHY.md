# 設計思想とアーキテクチャ解説 (Philosophy)

本ドキュメントでは、`antigravity-multiagent-setup-ja` がなぜこのルール体系・フック・サブエージェント構成を採っているのか、その背後にある設計思想を解説します。

---

## 1. なぜ「心がけ」ではなく「検証可能なプロトコル」なのか

LLM エージェントに「丁寧に実装してください」「バグがないかよく確認してください」と抽象的な指示を与えても、コンテキストが長くなるにつれて（Context Decay）、以下の失敗モードが必ず発生します：

1. **誤前提の無検証受容**: ユーザーの質問文や古い設計書に含まれる誤った前提（「関数 X が原因だと思う」等）を検証せずに突き進む。
2. **認知的閉鎖（Premature Closure）**: 最初に1つもっともらしい原因やファイルを見つけた瞬間に探索を打ち切り、並行して動いている別モジュールや別バージョンの存在を見落とす。
3. **テスト通過のためのプロダクション・テスト汚染**: テストが落ちたとき、アプリの真因を直す代わりにテストを `.skip` したり、実装の誤った出力をそのまま期待値にコピーして「テスト通過」と報告する。
4. **3ストライク固着（視野狭窄ループ）**: 同じ仮説のまま微修正を3回、4回と繰り返し、コードを複雑化させながら泥沼にはまる。
5. **コンテキスト汚染（Context Pollution）**: テスト実行の数百行の生ログや、大量のファイル検索結果、レビュアーの長文総評をすべてメインスレッドに流し込み、親モデルの推論精度を劣化させる。

本セットアップは、これら5つの構造的課題をそれぞれ独立した仕組みで解決しています。

---

## 2. 5つのコアメカニズム

### ① Tiered PAC と確信度の校正 (`GEMINI.md` §0.1, §0.4)
- すべての変更・コマンド実行の前に **「目的」** と **「予測（確信度XX%）」** を言語化し、実行後に **「照合: OK / 予測と異なる」** を出力させます。
- 予測と異なる結果が出た瞬間は「失敗」ではなく「メンタルモデルの誤りを教えてくれた最重要情報（サプライズの昇格 §0.2）」として扱い、闇雲な再試行ではなく原因仮説の立案を強制します。
- 確信度は主観ではなく**証拠の出自**で上限を決めます（学習知識のみの API・CLI・モデル名は確信度50%未満＝使用前の Grounding 必須）。

### ② 機械的ガードレール (`agy-harness` Lifecycle Hooks)
プロンプトのルールは忘却されることがありますが、`hooks.json` によるプロセス外スクリプトは 100% 発火します：
- **`guard_commands.py` (`PreToolUse`)**: `npm install` / `pip install` / `@latest` / `--no-verify` / `curl | sh` を実行前にブロックし、その場で `pnpm` / `uv` への最適解をエージェントに提示します。`rm -rf` や `git reset --hard` は `force_ask` で人間の承認を必須化します。
- **`guard_file_edits.py` (`PreToolUse`)**: テストファイルへの `.only()` / `.skip()` / `expect(true).toBe(true)` / 空 `except: pass` 混入を検知して警告します。
- **`session_context.py` (`PreInvocation`)**: 会話開始時と25ターンごとに今日の日付と基本原則を自動注入し、長時間の会話でも規律の風化を防ぎます。
- **`stop_selfreview.py` (`Stop`)**: エージェントが「完了しました」と止まろうとした瞬間に一度引き止め、当初の要求項目ごとの「済/未」と全主張への `exit code` / `file:line` 証拠併記をセルフレビューさせます。

### ③ 段階的合意と反証を組み込んだ 9ステップ `grill-me` / `grilling`
曖昧な要件に対して「1問聞いては少し調べ、また思いつきで聞く」場当たり的インタビューや、ゴール未合意のままいきなり関数レベルの TODO リストを作るアンチパターンを排し、3段階の Ask（②ゴール合意 → ④基本方針［**1項目1Ask・複数セクション混同禁止**］ → ⑦詳細TODO［**1項目1Ask**］）と2回の反証レビュー（⑥調査結果の反証・⑧計画の反証）を構造化しています。

### ④ 脱中心化（Mindfulness）と 15+3体クリーンルーム反証 (`multi-agent-kit`)
- **3ストライク時の脱中心化**: 3回連続で壁にはじかれたら、まず `mindfulness` スキルで「良い・悪い」「〜が原因のはず」という評価語を一切禁じた純粋事実（Facts）だけを観察させ、選択的注意（思い込み）を解除します。それでも打開できなければ `multi-agent-opinion`（モードB）または `ask-opus` で別アプローチを導出します。
- **クリーンルーム原則 (§3.4)**: レビュアーには「作成者の苦労話や言い訳」を一切渡さず、純粋な **Git 差分 ＋ 不変条件仕様（Invariants Spec）** のみを渡します。
- **単一責任15体 × 複眼3体**: 1体の汎用レビュアーに全部見させると表面的な指摘で終わるため、ステージ1では「時計・ライフサイクル分離」「UI計算式とロジックの二重化」「テスト通過用ハック検知」「データ移行のSSOT分裂」など極限まで絞った15体の Flash レビュアーを並列走査させ、ステージ2で「事実照合（ハルシネーション指摘の棄却）」「複数機能同時発火の組み合わせ攻撃」「システム全体のレイヤ整合性」の3視座から再検査します。

### ⑤ コンテキスト保護とモデル適応オーケストレーション (`claude-orchestrator-kit`)
- `Gemini 4 Carbon` や `Claude Opus` のような重量級・高推論モデルで毎回 `pnpm test` の数百行ログを読ませたり20ファイルを grep させると、思考トークンと待ち時間が膨れ上がります。
- そこでメインモデルは「設計・コア実装・最終目視と反証」に専念し、広域調査（`flash-investigator`）やビルド・テスト実行（`flash-runner`）は高速な Flash サブエージェントに逃がし、**「コマンドと exit code と要点3行だけ」** を受け取ることで、親スレッドのコンテキストを常にクリーンに保ちます。
