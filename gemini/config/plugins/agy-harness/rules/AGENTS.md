# agy-harness Rules (実装・運用規律 §4〜§11)

[事実] 本ファイルは `~/.gemini/GEMINI.md`(§0〜§2)と同時に常時展開されるプラグインルールです（節番号共通）。機械的強制（deny/ask）は Hooks が担い、本ファイルは判断の指針を定めます。改定履歴は `~/.gemini/HANDOFF.md` に集約します。

## 4. Implementation Discipline

### 4.1 完全実装
- モックや仮実装ではなく、完全に動作する実装を行います。
- マジックナンバーの埋め込みやデータのハードコードを避け、データ層は外部設定や定数として分離します。

### 4.2 根本原因に対応する修正とテストの多角的検証
- **テスト失敗時の本質対応**: 最適解はアプリケーションコードの修正です。skip、only、条件分岐でのテスト回避は設計上の問題シグナルとして扱い、理由を報告します。
- **仕様からの期待値導出**: テスト期待値はドメイン仕様・要件から導出します（実装の出力を安易にコピーして期待値にしない）。
- **テストの批判的検証**: テスト通過＝仕様の正しさとは限りません（過剰モック、不十分なアサーションの存在）。仕様・実装・テストロジック・fixture の多層から真因を特定します。
- **網羅性と決定論**: 正常系に加え、境界値・異常系・状態遷移を含めます。乱数・時刻・外部APIは注入可能にして固定します。
- **客観証拠による完了確認**: 修正前の事象を再現テスト等で確認し、修正後に意図通り動作することを行番号・ログ・exit codeで示します。

### 4.3 計画ファースト（条件付き）と `/grill-me` ワークフロー
以下の作業では、作業範囲内に `implementation_plan.md`（必要に応じて `task.md`）を作成して設計確認を行います:
- 複数ファイルにまたがる変更
- 大規模リファクタリングや設計変更
- 破壊的操作（削除・移行・スキーマ変更）
- 仕様が曖昧で前提のすり合わせが必要な作業
※ `/grill-me`（`<GRILL_ME>`）または `/grilling` 実行時や要件すり合わせ時は、ゴール未合意のままいきなりアクションリスト（TODO）に落とすことや小出しの質問ループを禁止し、必ずスキル `grill-me` / `grilling`（`~/.gemini/config/skills/grill-me/SKILL.md`）の9ステップ（①初期調査 → ②ゴール再確認Ask → ③複数の調査 → ④方針すり合わせAsk［1項目1Ask・複数セクション混同禁止］ → ⑤詳細調査 → ⑥調査結果の軽い反証レビュー → ⑦TODO詳細化Ask［1項目1Ask］ → ⑧反証レビュー＆Plan策定 → ⑨実装開始）に従います。
※単発修正、軽微なバグ修正、調査のみの場合は応答内に簡潔な手順を示して進めます。

### 4.4 不要コードの整理
- 自身の変更によって不要となった import・変数・関数は適切に整理します。元から存在していた未使用コードは状態を維持し、発見事項として報告します。

### 4.5 影響範囲の考慮
- 変更を加える際は、「Aを変更します。これによりBとCに影響します」の形式で波及範囲を調査・対応します。削除・上書きの前に対象を読み、一時退避は削除ではなくリネーム・移動を選択します。

### 4.6 Grounding（外部検索）と最新性の担保
- **対象**: 高速変化領域（ライブラリAPI・モデル名・CLI・価格・規約）は、着手前および判断前に公式ドキュメントまたは検索ツールで確認します。言語仕様やローカルコードは一次ソース（コード・仕様書・実行結果）で確認します。
- **識別子の検証**: 関数名、設定キー、CLIフラグ、モデル名等は存在を確認した出典を付記します。
- **複数ソース裏取り**: 最初に発見した情報は「候補」であり「答え」ではありません。更新日時・公式性を確認し、独立したソースで裏取りします。deprecatedマークや未参照コードはLegacyの兆候として報告します。

### 4.7 信頼境界と公式ソース優先の原則
- サードパーティツールや外部スキル（`SKILL.md` 等）は、公式ドキュメント・公式リポジトリを一次ソースとして確認します。二次情報を取り込む際は公式との差分と安全性を検証します。

## 5. Context Decay 対策

- 独立したタスクは適切な単位に分割し、完了時に成果物・検証結果・未解決事項を整理して引き渡します。
- subagent には明確な役割、成果物、使用スキル、実行フロー、検証条件を付与します。
- **subagent 起動の目安**:
  - 起動する: 並行調査、設計、大規模リファクタ、レビュー、専門タスクの並行処理
  - 直接実行する: 3行以内の修正、単発コマンド、既知の手順実行

## 6. Context Hierarchy

- **第1階層**: `~/.gemini/GEMINI.md`（§0〜§2）+ プラグイン `rules/AGENTS.md`（§3〜§11）。
- **第2階層**: `<project>/GEMINI.md` または `<project>/AGENTS.md`。
- **第3階層**: `.agents/rules/*.md`（frontmatter に `trigger` 必須）。
- **24,000 バイト上限規律**: ルールファイルは 1 本 24,000 バイトで切り捨てられます。編集後に `wc -c` で確認し、超過時は別プラグインまたはスキルへ分割します。
- **配置原則**: 普遍的原則をグローバルに、個別知識を下位に配置。エージェント名や体数等の変動情報は各 `SKILL.md` を SSOT とし、ルールへ複製しません。改定履歴は `~/.gemini/HANDOFF.md` に集約します。

## 7. 拡張機構の構成ガイドライン

- **Skill** (`~/.gemini/config/skills/<name>/SKILL.md`、プラグイン同梱は `plugins/<plugin>/skills/`): モデルが自律選択する専門知識。description に「何をするか」と「いつ使うか」を具体的に記載。Antigravity 専用スキルは `~/.gemini/config/` 配下で一元管理。
- **Subagent** (`~/.gemini/config/agents/*.md`、プラグイン同梱は `plugins/<plugin>/agents/`): 独立コンテキストで動作する専門エージェント。
- **レイヤ分離**: ルールファイルは普遍的運用ガイドラインのみを扱い、ライブラリ仕様や API 詳細は Skill へ分離。

## 8. パッケージサプライチェーン対策ガイドライン

パッケージの完全性・再現性・実行前検証を確保します:
- **推奨ツール**: JavaScript/TypeScript は `pnpm`（例: `/opt/homebrew/bin/pnpm` または PATH 上の `pnpm`）、Python は `uv`（例: `/opt/homebrew/bin/uv`、`~/.local/bin/uv`、または PATH 上の `uv`）を使用します。`npm` / `npx` / `pip` の直接実行は禁止です。
- **再現性の確保**: 依存バージョンは固定値とし、対応する lockfile (`pnpm-lock.yaml` / `uv.lock`) で管理します（`@latest` は禁止）。
- **既存運用の尊重**: 既存プロジェクトが `package-lock.json` や `requirements.txt` を正としている場合はその運用を尊重します。ツール移行はユーザー提案・合意を経て実施します。
- **実行前調査**: パッケージ作業前に lockfile、`packageManager`、CI設定を確認します。

## 10. 設定ファイルの配置と SSOT

- Antigravity 専用ルール・スキル・設定は `~/.gemini/config/` と `GEMINI.md` に集約し、他エージェント設定と干渉させません。
- 共通運用ガイドラインは `GEMINI.md` と各プラグインの `rules/AGENTS.md` を SSOT とします。

## 11. 機械的ガードレール (agy-harness Hooks) との連携

`~/.gemini/config/plugins/agy-harness/` の Hooks が安全境界の維持を補助します:
- `command-guard`: パッケージ操作の安全性確保（pnpm/uv 推奨）および不可逆コマンドの確認通知。
- `test-integrity-guard`: テストコードの健全性確保およびファイル削除時の確認通知。
- `trust-boundary-guard`: 外部URLアクセス時の信頼境界確認。
- `session-grounding`: セッション開始時・定期的な日付・基本プロトコルのリマインド。
- `completion-gate`: 完了前のセルフレビュー確認。

Hook 判定への対応:
- deny 時は提示された代替コマンド・推奨手順を採用します。
- ask / force_ask 時は操作対象・影響範囲・復元手順を整理してユーザー判断を仰ぎます。
- 完了ゲート等の確認メッセージ受信時は、§0.5 のセルフレビューを完了させてから終了します。
