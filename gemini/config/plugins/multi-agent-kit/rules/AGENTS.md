# Multi-Agent Subagent Orchestration Rules

[事実] 本プラグインのオーケストレーション仕様および詳細規律は、Progressive Disclosure（オンデマンド読み込み）に従い `multi-agent-opinion` スキル(本プラグイン同梱 `skills/multi-agent-opinion/SKILL.md`)に集約されています。
レビューパイプラインの実行時は同スキルを参照してください。

## 運用原則
- **オンデマンド発動**: 通常の作業では全15エージェントの仕様を常駐展開せず、レビュー依頼時または3ストライク到達時に `multi-agent-opinion` スキルをオンデマンド起動する。
- **コンテキスト保護**: サブエージェントの生ログ・全指摘行を親コンテキストに持ち込まず、アーティファクトファイルへオフロードする。
- **3-Strike PDCA**: レビュー実行時は最大3回まで自動PDCAサイクルを回し、CRITICAL残存時は人間にエスカレーションする。詳細判定基準はスキル仕様書に準拠する。

## レビュー規律(§3。`~/.gemini/GEMINI.md` と節番号共通)

## 3. Audit Independence

### 3.1 外部ツールによるレビューの実行ガイドライン
- 外部 CLI ツール（Claude CLI 等）を用いたレビューは、環境に導入されている場合またはユーザーからの明示的な指定があった場合に実行します。
- 外部ツールの未導入、ネットワーク、認証などの状況により利用できない場合は、ツールの状態を `status: external_review_unavailable` として記録し、**自動的に Antigravity 内蔵の独立サブエージェント（`mindfulness-inspector` / `carbon-verifier` / `multi-agent-opinion` / `second-opinion-lite`）へフォールバック**して客観的検証を完遂します。
- 取得できた証拠と未検証事項を整理し、必要に応じて判断を Human（ユーザー）へ引き渡します。

### 3.2 指定された検査対象をそのまま評価する
- レビュー対象が特定ファイル（例: `main.py`）と指定された場合は、対象ファイルの実内容を基準に評価します。
- fixture や類似ファイルは補助資料として区別し、合否は指定対象の実内容で判定します。

### 3.3 second-opinion ラウンド上限
- 同一差分に対する自動的な second-opinion は、過剰なループを防ぐため最大 2 ラウンドを目安とします。
- セキュリティ・認証・決済・データ破壊・状態遷移・非同期排他に関わる重要な差分では、最大 3 ラウンドまで適用可能です。
- ラウンド上限到達後は、取得済みの各レビュー結果・未検証事項・選択肢を Human へ引き渡し、判断を仰ぎます。
- **並行・併用レビュー**: 外部ツールレビューと Antigravity のサブエージェント（`multi-agent-opinion`、軽量版は `second-opinion-lite`）によるレビューは、多角的な欠陥検出のために併用可能です。統合時の重複排除および修正の決定権はメインエージェントが保持し、各レビュアーは互いに独立して評価を行います。

### 3.4 クリーンルーム・セカンドオピニオン規律 (Clean-Room Second-Opinion Protocol)
- **入力の隔離 (Context Sanitization)**: セカンドオピニオン（外部ツールまたは独立サブエージェント）に渡すブリーフには、客観的・中立的な視点を担保するため、**「Git 差分（追加・変更内容）」と「対象機能の不変条件仕様（Invariants Spec / docs / API契約）」を中心**として渡し、作成側の主観的な思考プロセスや暫定的な試行錯誤の経緯は含めない構成とします。
- **不変条件仕様（Invariants Spec）の提示**: レビュー依頼時は、機能ごとの INV-ID（例: INV-01 データ所有権、INV-02 キャッシュ対称性、INV-03 エラー伝搬等）や参照すべき公式仕様書（`docs/*.md` 等）を明確に指定することを推奨します。
- **反証・一次情報検証（zero-bias-audit）**: レビュアーからの指摘事項（バグ報告・懸念事項）は鵜呑みにせず、また放置することなく、実ファイル（`file:line`）および一次情報（ドキュメント・型定義）と照合し、CONFIRMED / REJECTED / UNVERIFIED を判定してレポートに記録します。

### 3.5 完了前レビューおよび検証プロセス (Completion Verification Process)
- **重要ロジック変更時の検証推奨**: 共有状態、認証・認可、クリティカルな状態遷移、外部API連携など、重大な影響を及ぼしうるコードの変更を行った場合は、クリーンルーム・セカンドオピニオンによるレビューを経て完了することを推奨します。
- **実装完了時の軽量監査の活用**: 実装作業を伴うタスクでは、完了報告を行う前に、必要に応じて `second-opinion-lite` サブエージェント（重大局面では `multi-agent-opinion` または `carbon-verifier`）を活用した客観的監査を行うことが推奨されます。
- **コンテキスト健全性の維持 (Context Preservation)**: サブエージェントの詳細ログや全指摘行を親エージェントのコンテキストに過剰展開することを避け、詳細レポートはアーティファクトファイル（`second_opinion_report.md` 等）へ出力し、親エージェントへは「指摘件数とレポートへのリンク」を共有する最小限のサマリー形式を推奨します。
- **静的チェックの柔軟性**: 静的チェックツールやフックを運用する場合、過剰適合を避け、一般的なリスクパターン（例外の不適切な握り潰し等）を検知しつつ、意図的なフォールバック設計（`// fallback:ok` 等）や用途別の設計を適切に許容します。

### 3.6 視覚的検証・画面証拠の独立監査規律 (Visual Verification PDCA Protocol)
- **画面・UI変更時の独立検証**: Web UI、アプリ画面、ゲーム画面、GUIコンポーネントの新規作成・変更作業では、親エージェントの自己評価のみで完了とせず、スクリーンショットを取得し `visual-verification-reviewer` または `carbon-verifier` サブエージェントによる客観的視覚解析・監査を行うことを推奨します。詳細は `visual-verification-loop` スキルに準拠します。
- **ゼロ・トレランス判定**: 画面検証のチェックリスト（Criteria）において、1項目でも未達・表示崩れ・重なり・文字欠損・デザイン不整合が存在する場合は `CRITICAL` 判定として即座に差し戻し、修正と再撮影・再検証のPDCAサイクル（最大3ラウンド）を実行します。
- **クリーンルーム検証**: サブエージェントには主観的な開発経緯や言い訳を渡さず、客観的な画像ファイルパスと合格基準のみを渡し、純粋な視覚エビデンスに基づく中立判定を担保します。
